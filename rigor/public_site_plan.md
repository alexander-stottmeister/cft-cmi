# Plan — public presentation of cft_cmi: README, interactive site, documentation
Written 2026-09-21. Target: the public-ready repository `cft-cmi` (private when this was written; public since 2026-09-22).
Nothing here touches the private companion; every artefact below is built only from our own material.

## 0. Constraints that shape the plan

C1 **No third-party material on the public surface.** The 178 page excerpts stay private. Every figure and
   every animation must be generated from our own numerics or be an original schematic. This is also why the
   site cannot simply screenshot the papers' figures of cited results.
C2 **PDFs are currently gitignored build products.** `*.pdf` is excluded, so a README link to `paper1/main.pdf`
   would be dead in a clone. Decision D2 below; until it is taken, the README links to the sources.
C3 **GitHub Pages on a private repository needs a paid plan.** On the free tier Pages serves public
   repositories only. The site can be built and previewed locally from day one; publishing waits for either a
   paid plan or the repository going public (Decision D1).
C4 **The browser cannot redo the mathematics.** Ball arithmetic, the SDPs and the modular Galerkin solves are
   out of reach in JavaScript. Split every module into: closed forms evaluated live, and heavy results shipped
   as precomputed JSON. Each JSON record carries the file it came from, so a reader can check it.
C5 **Status honesty is non-negotiable.** The papers' disclosure now states that `proved` and `numerical` are
   different claims. Every figure caption, module and documentation page must carry the same badge, and a
   numerical value must never be displayed as if it were a theorem.
C6 **Two documents do not build** (`implementation_C11.tex`, `referee_implementation_C11.tex`). Any CI that
   compiles the papers will go red until they are fixed. That is a feature, not an obstacle.
C7 **Effort is bounded by what already exists.** Four figures are already ours; the result tables are already
   text; the knowledge base already holds every statement with a status. Most of this work is assembly, not
   new computation.

## 2. Deliverable B — the interactive site

### Hosting and layout

Pages is served from `docs/` on `main`, with `.nojekyll`, so the same folder is both the documentation
subfolder of Deliverable C and the site root. No site generator, no build step for HTML: plain ES modules, so
that a clone opens `docs/index.html` in a browser and everything works offline.

    docs/
      index.html            landing page: the four results, each linking to its module
      explore/<module>.html one page per module, each self-contained
      lib/                  shared: plot.js (axes, curves, drag), mobius.js, katex/ (vendored, MIT)
      data/*.json           precomputed results, each record with its source file
      assets/*.svg          the figures, shared with the README
      *.md                  the documentation pages of Deliverable C

Vendoring KaTeX rather than using a CDN keeps the page working offline and avoids a third-party request from
a reader's browser. Total added weight is expected to stay under 3 MB.

### The data pipeline, and why it matters

`tools/build_site_data.py` reads the existing result files and writes `docs/data/*.json`. Every record is
`{value, error, source, line, status}` where `source` is a repository path. The site renders the source under
every number as a link into the repository. A number that no file supports cannot be displayed. `make check`
re-runs the extraction and fails if any JSON has drifted from its source file, so the site cannot silently
fall out of step with the numerics.

Module 6 is the one worth building first: it is the newest result, it is entirely closed-form, and it is the
only one where an animation shows something a static figure cannot, namely that two protocols with the same
starting block and single-interval conditioning land on the same map.

It must implement the UNCONDITIONAL rule, Theorem 5.2 of `network_corner_calculus.tex`, which places the
Schwarzian masses at the preimages of the junctions scaled by the later maps' derivatives, and then show the
junction form of Theorem 5.3 as the special case that holds under hypothesis (H). Implementing only the
junction form would teach a false theorem: (H) can fail when a step conditions on a union of chain intervals or
the chain starts from a single interval, and where it fails the naive corner measure is wrong. It does not
always fail in those shapes: VWZ 1(A) and 1(B) both condition on a union and both satisfy (H), 1(B) because its
two corners coincide, while "add D on C, then A on BC" does not. The module therefore tests (H) itself rather
than inferring it from the shape of the protocol, and flags a failing configuration rather than silently
drawing the wrong masses. Two behaviours of Theorem 5.2 must be drawn, not only described: a mass that moves
off its junction to the preimage under the later maps, and a corner that is swallowed by a later step and
contributes nothing, which is the single-interval-start failure. Theorem 5.2
is no more expensive in JavaScript than Theorem 5.3. For the same reason the Protocol 3 panel must say that
its map equals the over-compressed Theorem-A map up to post-composition with a global Möbius map, which is
why the two agree as fidelities and differ as point maps.

### Rules for every module

- Badges are per displayed claim, not per module, because a module mixes statuses: module 4 shows proved
  theorems beside `all-channel-optimum-value`, which holds only under H1, H2 and H3, so that one carries a
  `conditional` badge naming its hypotheses, and module 6 marks the junction form as conditional on (H).
  `numerical` is never styled like `proved`.
- A card that has never been refereed is not displayed until it has been. This currently excludes
  `circle-model-taper-suppresses-theta`, which module 5 is built around, so that referee pass is a
  prerequisite for module 5 rather than an afterthought. That pass has now run (REF-P0-TAPER, 2026-09-21):
  the card's data all reproduce, but its five-window sweep confounds window position with transition width,
  and module 5 must therefore show the two controls separately rather than as one slider.
- A "where this comes from" line: the document that proves it and the script that computed it, as repository links.
- Works without JavaScript for the text and the static figure; the animation is an enhancement, not the content.
- Dark and light themes, a 16px gutter, no horizontal scroll on a phone, and every control reachable by keyboard.
- No analytics, no external requests at runtime.

## 3. Deliverable C — the documentation subfolder

`docs/` carries, beside the site, a navigable set of Markdown pages. GitHub renders them in the repository and
Pages serves them as part of the site, so one folder serves both readings.

    docs/index.md          the map: four results, ten modules, the five sections below
    docs/status.md         every claim, grouped by area, with status, one-line statement and links
    docs/notation.md       the symbol table
    docs/definitions.md    the objects and what they mean
    docs/results/<id>.md   one page per consequential claim
    docs/open.md           the open problems, with the next step recorded for each
    docs/sources.md        every external result relied upon, and whether it can be obtained
    docs/history.md        phases 1 to 6, what each settled, and the errata

**Generated, not hand-written.** `tools/build_docs.py` reads the knowledge base and emits `status.md`,
`results/*.md`, `open.md` and `history.md`; `make check` fails if the committed files differ from a fresh
generation. This is the only way these pages stay true as the mathematics moves, and it makes the private
knowledge base the single source of truth without publishing the knowledge base itself.

`notation.md` and `definitions.md` are assembled from `paper1/app_conventions.tex`, `paper2/app_conventions.tex`
and the conventions block of `rigor/phase6_brief.md`, then edited by hand once; a checker verifies that every
symbol used in the results pages appears in the table.

`sources.md` is generated from `refs/REFERENCES.md` and marks each of its 36 table rows as fetchable by
`refs/restore.sh`, open access, or needing library access, which is the information a reader actually needs and
which a referee found we had stated wrongly before. It cannot claim to list every external result relied upon:
the private companion holds 47 PDFs, and several are cited only as bullet entries rather than table rows, so the
page says what it covers and links to `REFERENCES.md` for the rest.

## 4. Build, CI and the gates

One `Makefile` at the root:

    make figures   tools/make_figures.py    -> docs/assets/*.svg
    make data      tools/build_site_data.py -> docs/data/*.json
    make docs      tools/build_docs.py      -> docs/*.md, docs/results/
    make papers    pdflatex both papers and the key rigor documents
    make check     regenerate everything into a temp dir and diff; non-zero on drift
    make site      figures + data + docs, then a local preview server

A GitHub Actions workflow runs `make check` and `make papers` on every push, and deploys `docs/` to Pages when
Pages is enabled. Consequences worth stating: CI is red until the two broken documents are fixed, and the
workflow compiles without the excerpts, so it also proves continuously that a public clone still builds.

### Omissions to close in the same work

- `CITATION.cff` at the root, so GitHub offers a citation, and a Zenodo deposit for a DOI once the papers are
  on arXiv. Without one the repository cannot be cited except by URL.
- `.github/`: an issue template that asks which claim and which status a report concerns, and the Actions
  workflow of section 4. A public repository without either collects unusable issues.
- `plan_page/petz_program_plan.html` is already public in the repository and frozen at 10 September, so it
  now contradicts the current state. Either it is regenerated as module 10 of the new site and deleted, which
  is the recommendation, or it is clearly marked as a historical snapshot.
- A size budget: the figures, the vendored KaTeX and the JSON should stay under 3 MB together, keeping the
  public repository under 10 MB.

## 5. Sequencing, effort and who does what

| phase | work | agent | referee |
|---|---|---|---|
| P0 | referee pass on `circle-model-taper-suppresses-theta`, which has never been reviewed | one Opus referee | it is itself the pass |
| P1 | `tools/make_figures.py`, figures F1-F5, README rewritten | one Opus agent | one pass, checks every number in a caption against its source |
| P2 | `tools/build_docs.py`, the eight documentation pages, the drift check | one Opus agent | one pass, checks generation is faithful and statuses are not upgraded |
| P3 | site skeleton, shared `lib/`, modules 1, 2, 6 | one Opus agent | one pass, including that no module displays an unsourced number |
| P4 | modules 3, 4, 5, 7, 8, 9, 10 | two Opus agents in parallel, disjoint module sets | one pass over both |
| P5 | Makefile, Actions workflow, Pages enablement | orchestrator | the workflow is its own check |

P0 must precede P4, because module 5 is built around a card that has never been refereed and the display rule
above bars an unreviewed card. P1 and P2 are independent and can run together. P3 must precede P4 because it
fixes the shared library. The
whole set is four to six agent-days of work, dominated by P3 and P4.

Rough token cost, extrapolating from Phase 6: 0.8M to 1.2M per building phase and 0.2M to 0.4M per referee
pass, so 4M to 6M in total. If that is too much, the honest reduction is to cut P4 to modules 4 and 6 and ship
the other results as static figures; the coverage table then states plainly which results are interactive.

## 6. Decisions — taken 2026-09-21 by the user

D1 **Pages goes live only when the repository goes public.** The site is built, committed and previewed
   locally from now on; the Pages deployment step of P5 is written but left disabled, and enabling it is one
   line plus one click once `CHECKLIST.md` is clear. No paid plan is needed.
   Done 2026-09-22: the three steps were taken in this order -- the repository was made
   public, Pages was enabled by a REST call with a user token and build_type workflow, and the
   `if: false` came off the deploy job. The site serves.
D2 **PDFs as recommended: releases now, continuous integration once it is green.** Each release carries
   `paper1` and `paper2` as attached assets, so a citation points at a fixed version rather than at a moving
   file, and the README links to the latest release. When the two broken documents build again, the workflow
   also publishes the current PDFs under `docs/pdf/` as a Pages artefact, without committing them, which keeps
   the `*.pdf` ignore rule intact. The first release is `v0.1.0-draft`, marked pre-release because the papers
   are drafts and the repository was private when the tag was cut.
D3 **All ten modules.** Coverage stays as tabled: 33 refereed-or-proved claims plus 11 headline numericals.
D4 **The site carries the AI-provenance text**, in the same words as the papers, on the landing page rather
   than on a subpage, and every module keeps its per-claim status badge.
